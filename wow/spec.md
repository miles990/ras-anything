# RAS-anything v0.1 — spec (wow 輕量交付 + 七關)

Owner: Alex Lee (miles990). Request (2026-11-23, pt507u): 取 fast-anything 設計核心，fast → Reliability, Availability, Serviceability；用 Claude Fable 當 wow 評審；新建 repo 做 RAS-anything。

## First-principles check
- **facts**: fast-anything's value = (1) measure, don't guess; (2) touch only the weakest few units; (3) a coding agent writes the change; (4) *proof* on real recorded behaviour before swap; (5) reversible swap (marked block + kill switch). None of that is specific to speed. RAS failures in small Python services come overwhelmingly from the *boundary* (network/subprocess/IO): no timeout → hang, no retry → transient error becomes outage, retry without idempotency → duplicate side effects, swallowed exceptions → silent wrong data, no context in errors → slow diagnosis.
- **constraints**: no paid tools; private repo; no publish/post; CI budget tight; Fable judge-only; no fabricated numbers; MIT credit to fast-anything; builder ≠ judge.
- **goal**: one command that shows, with measured numbers on the user's own workload, how much more available a Python app becomes under realistic dependency faults after hardening only its weakest function(s) — and proves the happy path did not change.
- **rebuild (smallest mechanism)**: Python-only, stdlib-only tool (no Rust: reliability is control flow, not CPU; the target apps are Python; zero-dep install). Fault injection at the boundary (monkeypatched `urllib.request.urlopen`, `subprocess.run`, optional `requests`), deterministic seeded fault plans, outcome classification per call. Node deferred (prove the loop in one language first).
- **decision-seat**: internal gates = AI (Fable 5-1 judge, Codex second opinion); anything external (making repo public, publishing, posting) = Alex.
- **verdict**: proceed (reshape fast→RAS as above).

## External spec items (S-n)
- S-1 `ras-anything scan -- <cmd>`: runs the user's workload once clean and once under seeded chaos; static+dynamic signals per top-level function (boundary calls without timeout, no retry/backoff, bare/swallowing except, non-idempotent writes retried, missing error context/trace id, unclosed resources); ranks by **risk × exposure × hardenability**; prints a ranked table with ids and a one-line "why" + verdict (harden it / can't yet: reason).
- S-2 `ras-anything harden [id] [--agent claude|codex|<cmd>]`: re-runs workload, records up to 500 real calls of the unit (args, return, and the boundary I/O it performed — VCR style), creates `.ras/hardens/<id>/` with `hardened.py` stub + `TASK.md` (contract: same happy-path results; bounded latency; declared fallback; idempotency rules; structured errors). With `--agent`, pipes TASK.md to the agent.
- S-3 `ras-anything verify [id]`: (a) happy-path replay: every recorded call, boundary served from recordings, hardened result == original result (exceptions: same type where original raised); (b) chaos replay over a fixed fault matrix (timeout/hang, connection refused, HTTP 5xx, slow dependency, truncated body, sustained outage then recovery), original vs hardened; (c) safety checks: no new crash types, p99 latency ≤ budget, no added duplicate non-idempotent side effects (POST/PUT without Idempotency-Key), fallback values only those declared. Enable is refused unless all pass AND availability strictly improves.
- S-4 `ras-anything enable|disable [id]`: appends / removes one marked block to the function's module (byte-for-byte removal, checked by hash). `RAS_ANYTHING_DISABLE=1` forces originals at runtime.
- S-5 `ras-anything bench -- <cmd>`: whole-app runs under seeded chaos, interleaved original vs hardened, N seeds; reports availability % (correct-or-declared-degraded within budget), error/crash rate, p50/p99 latency, duplicate side effects, recovery calls after outage.
- S-6 `ras-anything report`: `RAS-REPORT.md` + `ras-card.svg` (before/after, honest labels: fault model, seeds, machine).
- S-7 `ras-anything doctor`: python version, agents (claude/codex) on PATH, git cleanliness, write access.
- S-8 `ras-anything go --agent <a> -- <cmd>`: scan → harden top → verify → enable → bench → report in one command.
- S-9 Agent surfaces: stdio MCP server (`ras-anything mcp`, tools ras_scan/harden/verify/enable/disable/bench/report/status), Claude Code plugin (`.claude-plugin/`, `commands/ras.md`), `skills/ras-anything/SKILL.md`.
- S-10 Runtime helpers `ras_anything.runtime` (stdlib): `timeout`-aware call, retry with full jitter + budget, circuit breaker, fallback, structured error with trace id + JSON log line. Hardened code may use them.
- S-11 Two realistic example apps in `examples/` with reproducible before/after numbers produced by actually running the pipeline (hardened code written by a real coding agent run, kept in repo).
- S-12 README: pitch, install (pip install -e / pipx from git), use table, proof section, measured results table (only measured), fault model, limits, credit to fast-anything (MIT).

## Domain points (W6)
Timeouts must be on every blocking boundary call; retries only on transient errors (timeouts, connection errors, 502/503/504, 429 honoring Retry-After), never on 4xx; exponential backoff with full jitter and a total time budget; never retry non-idempotent writes without an idempotency key; circuit breaker opens after consecutive failures and half-opens after cooldown; fallbacks must be explicit and distinguishable (degraded), never silent wrong data; errors carry cause + context + trace id; swallowing exceptions is a defect. Availability = good / valid requests within a latency SLO (Google SRE definition). Chaos must be deterministic (seeded) to be comparable.

## Wow moment (gap type ①②③)
"咦？這樣就好了？" — one command on your own app prints *availability under faults 61% → 99%* with the hardened diff being ~30 lines in one function, and verify shows the exact recorded call that the naive retry would have double-charged. Not arrived = numbers only on a toy that the tool was tuned for; or hardened code that "passes" by swallowing everything.

## Main flow & first-use target
`pip install -e .` → `ras-anything go --agent claude -- python examples/weather/app.py`. First-use (without README) target: understand ranked scan output and what to do next ≤ 30 s of reading (LLM proxy, marked 未驗效度).

## V-8 Serviceability made real and measured (2026-11-23, Alex steering)

### Research → convergence (first-principles-check)
- **Sources**: Google SRE book (monitoring "symptoms vs causes", MTTD/MTTR as incident phases, playbooks/runbooks cut MTTR — SRE ch.1 cites ~3× MTTR improvement from playbooks); DORA 2024 five metrics (failed deployment recovery time — renamed from MTTR/time-to-restore in 2023 — and change fail rate; dora.dev/guides/dora-metrics); ISO/IEC 25010:2023 maintainability = modularity, reusability, **analysability**, **modifiability**, **testability**; OpenTelemetry log data model (Timestamp, SeverityText, Body, TraceId, SpanId, Attributes) + stable HTTP semconv (`error.type`, `server.address`, `http.request.method`, `http.response.status_code`, `http.request.resend_count`); health checks (liveness/readiness, breaker state exposed).
- **facts**: in RAS-anything's harness the injected fault is *ground truth* (we know which dependency and which fault class, at which virtual-clock tick). So "could someone diagnose this from the logs alone?" is objectively scorable without humans or LLMs. Swallowed errors make detection impossible; bare tracebacks usually name the exception but not the dependency (host/route/argv) or whether retries happened. Rollback of a RAS change = `disable` (marked-block removal) or `RAS_ANYTHING_DISABLE=1`; its duration is directly measurable.
- **constraints**: every metric reproducible from seeds + virtual clock; no vanity (no "log lines count", no LOC); no LLM in the measured path (deterministic diagnoser), stdlib/no-npm-deps; works for Python and Node identically (language-neutral JSON).
- **goal**: show, measured, that a hardened function is faster to detect, correctly diagnosable from logs alone, and restorable in seconds — before vs after.
- **rebuild**: (1) runtime helpers (Python `ras_anything.runtime`, Node equivalent) emit OTel-log-data-model JSON lines (one per dependency failure / retry / breaker transition / fallback) with trace_id/span_id correlation and attributes `ras.dependency`, `server.address`, `error.type`, `http.response.status_code`, `http.request.resend_count`, `ras.breaker.state`, `ras.idempotency_key`, `code.function`; via stdlib `logging` (Python) / stderr JSON (Node); `OTEL`-compatible so it can be shipped to any collector. (2) health: `runtime.health()` / Node `health()` returns breaker states; optional snapshot file (`RAS_ANYTHING_HEALTH_FILE`) that `ras-anything status` reads and shows. (3) `report` auto-generates `RUNBOOK.md` per hardened function (dependencies touched, faults handled and how, log query to find them, breaker meaning, how to disable/rollback, verify evidence links). (4) a deterministic **log-only diagnoser** (`ras_anything/diagnose.py`) that reads only the app's stdout/stderr of a faulted run and outputs {detected, dependency, fault_class}; scored against ground truth.
- **measured metrics (verify + bench, original vs hardened, same seeds)**:
  - **Detection rate** and **TTD** (time-to-detect, virtual clock ticks/ms from fault injection to first diagnostic record that identifies a failure; ∞/"not detected" if none).
  - **Diagnosis accuracy** (share of faulted runs where the diagnoser names the right dependency AND fault class from logs alone) and **lines-to-diagnosis** (log records read before the correct one; a reproducible proxy for time-to-diagnose).
  - **Time-to-restore** (wall seconds for `ras-anything disable` to restore byte-exact original + post-restore smoke pass; and kill-switch path), modeled as DORA failed-deployment recovery time for a deliberately bad enable in a test fixture.
  - All shown on the report card + RAS-REPORT.md before/after; unavailable → "unavailable", never 0.
- **decision-seat**: AI internal (Fable/Codex); verdict: **proceed**.

## V-13 Resilience pattern catalog (best professional practice, measured keep/reject)
References: Nygard *Release It!* 2e stability patterns (timeouts, circuit breaker, bulkhead, steady state, fail fast, let it crash, handshaking, test harness, decoupling middleware, shed load, create back pressure, governor); Google SRE book ch.21–22 (handling overload, cascading failures: per-request retry cap, per-client retry budget ~10% ratio, deadline propagation, load shedding, adaptive throttling); AWS Builders' Library "Timeouts, retries and backoff with jitter" (full jitter, token-bucket retry quota), "Making retries safe with idempotent APIs" (client request token), "Using load shedding to avoid overload"; AWS Well-Architected Reliability pillar (REL05: throttle, retry w/ backoff limits, fail fast, idempotency, constant work, timeouts); resilience4j (CircuitBreaker sliding window + half-open probe count, Bulkhead semaphore/threadpool, RateLimiter, Retry, TimeLimiter), Polly v8 / Microsoft.Extensions.Resilience (standard pipeline: rate limiter → total timeout → retry → circuit breaker → attempt timeout; hedging), Failsafe (fallback, retry, CB, bulkhead, timeout, rate limiter, hedge policy). IETF draft-ietf-httpapi-idempotency-key-header (Idempotency-Key semantics: key per logical operation reused across retries, 409/422 on conflicts).
Candidate set: attempt timeout + total deadline (with deadline propagation to nested calls); retry with full jitter + max attempts + **retry budget (token bucket, ratio of retries to requests)**; honor Retry-After/429; circuit breaker (count/rate based, half-open probes); **bulkhead** (per-dependency concurrency cap); **rate limiting / load shedding** (client-side, adaptive throttling per SRE formula max(0,(requests − K·accepts)/(requests+1))); **hedged requests** (idempotent reads only, after p95 delay, cancel loser); **fallback hierarchy** (fresh → stale cache within TTL → declared degraded value → error); **standard Idempotency-Key** (one key per logical op reused across attempts); **adaptive concurrency** (AIMD/gradient limit).
Decision rule: implement each in the runtime helpers of every language (common semantics, documented), then measure each pattern ON vs OFF on the examples + a dedicated overload/retry-storm scenario with the seeded virtual clock. Keep a pattern (default-on in the TASK.md guidance / runtime defaults) only if it measurably improves availability, p99, duplicate effects or **retry amplification** without breaking happy-path equivalence; otherwise ship as opt-in or reject, with numbers. 
New metric: **retry amplification** = dependency attempts / logical calls (and under outage: attempts during outage window per logical call); reported in verify/bench/report/SLO card. Catalog with references + measured keep/reject table in `docs/PATTERNS.md`.

2. Hot update without restart: file-watch/poll (Python, Node; Go via config reload goroutine) with atomic swap + last-known-good on invalid config; enable/disable/swap hardening at runtime through the flag. Proof: a long-running process under steady load (seeded), flip flags N times; measure switch latency (flag write → first call using new value; p50/p99) and dropped/failed requests = 0. Evidence + test.
3. Modularity: patterns are plugins (`ras_anything/patterns/<name>.py` + per-language equivalents) with a registry and a contract test suite each; adapters independent modules with per-adapter tests; docs/ARCHITECTURE.md module map + dependency rules (core ↛ language specifics; patterns ↛ adapters).
4. Flight recorder: bounded ring buffer in each runtime capturing call context (function, redacted inputs — secrets/PII redaction rules, hashes), fault, retry/breaker/bulkhead/fallback decisions, trace id; dumped to `.ras/incidents/<id>.json` on failure/trigger. `ras-anything replay <incident-id>` deterministically reproduces it (cassette + seed + virtual clock) and writes an RCA report (failing dependency, fault type, decision chain, first divergent decision, suggested fix). Measured: blind injected incidents (generated by a script with hidden ground truth) → reproduction rate, root-cause accuracy, time-to-diagnose.

## V-17 Blast-radius minimization
Research basis: progressive delivery (Argo Rollouts / Flagger: canary steps, analysis templates on metrics, auto-promote/abort), cell-based architecture (AWS: cells, shuffle sharding), bulkheads (Release It!), fail-open vs fail-closed safe defaults, guardrail metrics with auto-rollback, dark launch / shadow traffic (traffic mirroring, compare, serve primary).
1. Progressive enable: `ras-anything enable <id> --canary 5,25,50,100` routes that % of calls (sticky by key hash) to the hardened code; analysis gate on SLIs (availability, p99, error rate, dups, semantic success) original vs canary over a window → auto-promote or auto-rollback (flag flip, logged with reason).
2. Shadow mode: `--shadow` runs hardened alongside original for real calls with side effects suppressed (boundary served from the original's recorded I/O / no writes), compares outputs, always serves original; promotion only after N matching calls.
3. Fault isolation scope: breaker/bulkhead/budget state scoped per dependency and optionally per key (shuffle-sharded), per function; prove one failing key/dependency doesn't trip others.
4. Safe defaults: any exception/bug inside ras runtime helpers, flag evaluation, recorder or canary router must fail back to the ORIGINAL behaviour (fail-safe), never worse; fault-inject the hardening layer itself in tests.
5. Measure blast radius: injected incidents (bad hardening, dependency outage, poison key) → % requests affected and time to automatic containment (virtual clock), before vs after (no canary/no isolation vs canary+isolation). Report in report/SLO card.

## V-18 Agent Experience (AX): agent-readable failures (Alex 2026-11-23, inspired by 安德魯的部落格 2026-11-20)
- When a hardened call ultimately fails, raise/return a structured error (exception subclass carrying the data; `str()` = short plain text; `.to_json()` / `.problem` = RFC 9457 problem+json shape: `type` (URI per cause category), `title`, `status`, `detail` (masked), `instance` (correlation id) + extensions): `cause` (timeout|unavailable|rate_limited|quota|invalid_request|auth|conflict|dependency_bug|unknown), `dependency` (logical name, not host), `retryable` bool, `retry_after_s`, `next_action` (retry_later|change_params|use_fallback|escalate|stop), `needs_human_authorization` bool, `correlation_id` (= trace id). PII masking (emails, phones, card numbers, tokens) and never leak internals (stack traces, hosts/IPs, file paths, secrets) — tested by a leak scanner over all emitted errors.
- Human-gate hook pattern: `runtime.require_approval(op, details)` for irreversible ops (charges, deletes, sends): pluggable approver (callback/env/file), default deny in non-interactive runs → error with `needs_human_authorization=true`, `next_action=escalate`. Documented in docs/PATTERNS.md + tested.
- Measured AX metric: in seeded injected failures, a deterministic scripted policy agent (and optionally the recorded/mock LLM agent from V-14 — no paid API) reads ONLY the error surface (stderr/exception text) and chooses the next action; scored vs ground-truth correct action. Report accuracy, tokens (len/4 estimate of what the agent had to read) and steps to resolution, original (generic error/traceback) vs hardened. In verify/bench/report.
- Python + Node runtimes now; all later language runtimes must implement the same error shape.
